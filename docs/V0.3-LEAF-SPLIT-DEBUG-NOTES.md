# v0.3 leaf-split silent-orphan bug — debug notes

## TL;DR

After ~4 LARGE_INDEX leaf splits in the same directory, a subsequent insert
(or write — unclear which yet) silently loses ~10-15 previously-inserted
`$I30` entries from disk. The MFT records themselves remain (IN_USE=1) but
no longer appear in the directory's `$INDEX_ALLOCATION` tree.

This was confirmed against a real 4 TB WD My Passport drive during the
v0.2.0 hardware-validation session: copying 63 files into a fresh
directory left 11 MFT records reachable only as orphans.

## Reproduction

- Test: `Tests/NTFSCoreTests/StreamingAndLargeIndexTests.swift` →
  `testLeafSplitOrphansBugUnderCpRWorkload` (currently `XCTSkip`'d
  pending fix; remove the skip to reactivate).
- Pre-grows `$MFT.$DATA` twice via `growMFTDataByClusters(8)` to get
  enough slots past the small-fixture cap.
- Then runs `createFile + write` per iteration in a loop on the LARGE_INDEX
  root (matches `cp -r`'s per-file shape).
- Final reopen check: every inserted name should appear in `enumerate`.
  It doesn't — entries from the 4th leaf-split onward vanish.

## What's been ruled out

| Hypothesis | Status |
|---|---|
| The split itself drops entries during bisection | **Ruled out.** Added `splitLeafAndPromote` self-verifier that compares pre-split tree state ∪ {new entry} vs post-split tree state. Never fires across the reproduction. |
| `mergeAdjacentExtents` corrupts the `$INDEX_ALLOCATION` runlist | **Ruled out.** Disabling the merge produces identical orphan pattern. |
| Allocator hands out a cluster already in a leaf | **Ruled out.** Added a per-split sanity check comparing `newLCN` against existing `$INDEX_ALLOCATION` extents — never fires. |
| In-memory cache shows entries that aren't on disk | **Ruled out.** Per-iteration reopen-from-disk check confirms entries present *during* the iterations. They disappear only between the last iter and the test's final reopen. |

## Strongest remaining hypothesis

**A later operation overwrites a leaf cluster that the volume bitmap thinks
is allocated.** The corruption fires between iter 70 and iter 75-ish — the
window where (a) the 4th split fires and (b) subsequent inserts cause more
writes. Per-split state-walks pass; per-iter live reads pass. Yet the
final reopen-from-disk fails.

Possible mechanisms (in decreasing likelihood):

1. **`mft.writeRawRecord` for an MFT slot in a freshly-grown `$MFT.$DATA`
   extent lands at the wrong byte offset** because the cached
   `_mftDataExtents` got stale relative to disk between growth events
   and a subsequent split's parent-record rewrite. The runlist-aware MFT
   reader in `MFT.mftRecordByteOffset` uses `_mftDataExtents` but
   invalidation isn't tight.
2. **`splitLeafAndPromote`'s left-leaf rewrite (at `leafByteOffset`)
   overwrites bytes that include another leaf's region** because
   `leafByteOffset` was computed against a stale runlist.
3. **The new `$INDEX_ROOT` body's interior-entry serialization** writes
   a subnode VCN that matches an existing leaf's VCN, causing descent
   to find the wrong leaf — the original leaf becomes unreachable from
   the tree (= orphan).

## Recommended next steps (for a focused fresh session, ~3-4 hours)

1. Reactivate the test (`testLeafSplitOrphansBugUnderCpRWorkload`).
2. Add `dd if=/dev/diskN bs=4096 count=N | xxd` style byte-range dumps
   **before and after every split's per-leaf and per-parent write**.
   Diff them against the expected mutations. The first divergence is
   the bug.
3. Specifically dump:
   - The leaf at `leafByteOffset` before + after the LEFT-leaf rewrite.
   - The cluster at `newLCN * clusterBytes` before + after the
     RIGHT-leaf write.
   - The parent MFT record before + after `rewriteParentForLeafSplit`.
   - The volume bitmap snapshot at each step.
4. After identifying the diverging write, the fix usually drops out
   immediately (it's a wrong byte-offset, a stale cached value, or a
   miswritten field).

## In-place tooling that helps

- `Volume.splitLeafAndPromote` already runs a pre-/post-split entry-set
  check that throws with a detailed report if the split itself drops or
  duplicates entries. **Keep this in place** — it's a robust safety net
  for any future regression and was confirmed not-fired in this bug.
- `Volume.collectAllFileRefsInLargeIndex` walks the full tree and
  returns the fileRef set; useful for any further differential checks.

## What v0.2 ships with

- Leaf split enabled; works correctly for the first 1-3 splits per
  directory (~50-150 files in a fresh subdirectory depending on name
  length).
- Anyone copying more files than that into a single fresh subdirectory
  hits the orphan bug — **silent partial data loss** that requires
  `chkdsk /f` or `ntfsfix` to reclaim the orphan MFT slots.
- STATUS.md / README warn about this.

## What v0.3 needs to ship

- Either fix the bug per "Recommended next steps" above.
- OR ship the safe-cap auto-chunking fallback (in `Tools/ntfsctl/Sources/ntfsctl/Cp.swift`):
  when `cp -r` is about to insert into a fresh directory that already has
  N entries (where N is conservatively `30`), create a sibling
  directory `dirname-part2/` and continue there. Ugly but completely
  sidesteps the bug.
